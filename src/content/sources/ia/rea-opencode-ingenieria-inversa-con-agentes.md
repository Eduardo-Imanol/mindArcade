# REA + OpenCode: Guía Técnica de Ingeniería Inversa con Agentes

## 0. Alcance de esta guía y qué es REA realmente

Antes de entrar en profundidad, conviene fijar los hechos: REA (`morluto/rea`, licencia MIT, distribuido como el paquete npm `rea-agents`, sitio oficial `rea.tools`) es un proyecto real y muy activo — del orden de cientos de miles de estrellas en GitHub — que expone un servidor MCP único con más de 120 herramientas tipadas organizadas en familias (binarios nativos, JavaScript/Electron, .NET, Android, firmware, capturas de red, bases de datos SQLite, metadatos de modelos GGUF/safetensors, bytecode EVM, objetos de código GPU, etc.).

Dos puntos estructurales que cambian cómo debes leer el resto de esta guía:

1. **REA es, ante todo, una plataforma de análisis "evidence-first" de solo lectura**, no un parcheador de binarios. Cada herramienta devuelve hallazgos junto con su evidencia, sus límites y sus "unknowns" explícitos — "not found" o "not supported" es una respuesta válida, no un error. La única escritura que REA aplica a un binario es la **anotación no destructiva** (renombrar funciones/direcciones y añadir comentarios) dentro de la base de datos efímera de Ghidra o Hopper — nunca modifica los bytes ejecutables del artefacto original. Si tu objetivo final es parchear un binario, inyectar código, recalcular checksums o reconstruir cabeceras, eso vive en una categoría de herramientas distinta (editores hexadecimales, LIEF, scripts de Ghidra/Keystone, parcheadores dedicados) que no forma parte de la superficie de REA. Te doy el marco conceptual de cómo funciona el patching en general (sección 4.4), pero no voy a construir contigo un procedimiento operativo para desactivar comprobaciones de licencia o DRM de software de terceros: el propio `DISCLAIMER.md` del proyecto es explícito en que REA "es para investigación legal, educación, interoperabilidad, preservación de software y análisis de software que posees o estás autorizado a examinar", y prohíbe expresamente el uso de copias crackeadas, claves robadas o la evasión de restricciones de licencia — incluidas las de las propias herramientas comerciales (IDA Pro/Hex-Rays, Hopper, JEB) que REA puede pilotar. Esto no es un matiz legal menor: define qué tipo de flujos de trabajo tiene sentido automatizar con este stack.
2. **OpenCode es igualmente real**: es el agente de codificación de terminal open-source (CLI/TUI) que se configura vía `opencode.json` (global en `~/.config/opencode/` o por proyecto), con secciones para proveedores de modelo, servidores MCP (`mcp`), agentes personalizados (`.opencode/agents/*.md`), skills auto-descubiertas (`.opencode/skills/*/SKILL.md`), comandos (`.opencode/commands/*.md`) y plugins JS/TS (`.opencode/plugins/*.js`). REA figura explícitamente como cliente soportado por su instalador (`--client opencode`), lo cual simplifica mucho el bootstrap, como verás en la sección 3.

Con ese marco, vamos a la arquitectura.

## 1. Fundamentos arquitectónicos y el protocolo MCP en REA

### 1.1 El servidor como proceso Node.js

REA se distribuye como CLI y daemon MCP unificados escritos en TypeScript/Node.js (requiere Node 22.x ≥22.23.4, 24.x ≥24.22.1, o 26.12.1+). El punto de entrada es el paquete `rea-agents`; `npx rea-agents setup` resuelve el runtime, instala el script de entrada de REA y registra tanto el servidor MCP como un conjunto de "workflow instructions" (la skill de investigación) en el agente elegido. El CLI `rea` y el servidor MCP comparten exactamente la misma capa de lógica de negocio — una llamada a `rea decompile` y una llamada MCP a `decompile` ejecutan el mismo código, lo que garantiza paridad entre el flujo interactivo humano y el flujo dirigido por agente.

### 1.2 Transportes: stdio y HTTP/Streamable

El modo por defecto es **stdio**: el agente lanza REA como proceso hijo (`npx -y rea-agents@<versión> mcp`) y se comunica por los flujos estándar de entrada/salida — es el modelo MCP "local server" clásico, de ciclo de vida acoplado al proceso del agente. Para escenarios donde quieres desacoplar el servidor del agente (contenedores, servidores compartidos, bridges remotos), REA también se expone sobre **Streamable HTTP**: por ejemplo, la imagen Docker oficial `psyb0t/reverse-engineer-anything` levanta un endpoint `http://localhost:8080/mcp` que un cliente stdio-only puede alcanzar mediante un bridge, o que un cliente con soporte HTTP nativo añade directamente como `--transport http`. Para analizar binarios de Android dentro de un contenedor con JADX/Apktool/adb ya preinstalados, este patrón HTTP es el habitual, porque evita instalar toda la cadena de herramientas nativamente en el host del agente.

La elección de transporte no es solo de conectividad: con stdio, el ciclo de vida del proceso REA (y por tanto el estado de sesión que mantiene — bases de datos Ghidra abiertas, procesos Hopper, etc.) muere con el agente; con HTTP, puedes mantener sesiones de análisis vivas entre reinicios del agente o compartirlas entre varios clientes MCP apuntando al mismo endpoint.

### 1.3 Perfiles de esquema y presupuesto de contexto del tool-list

Con más de 120 herramientas tipadas, el simple acto de anunciar el catálogo (`tools/list`) puede consumir una cantidad significativa de contexto antes de que se haga una sola llamada. REA expone dos controles orientados exactamente a este problema:

- `REA_MCP_INPUT_SCHEMA_PROFILE` (`compact` por defecto, o `full`): el perfil compacto reduce la verbosidad de los esquemas de entrada anunciados; el perfil completo expone cada campo con su guía de validación anidada completa — útil cuando estás depurando por qué una llamada falla validación, pero caro en tokens para el uso normal.
- `REA_MCP_OUTPUT_SCHEMA_PROFILE` (`compact`, o `off` para omitir esquemas de salida por completo): algunos clientes MCP truncan el frame `tools/list` si es demasiado grande; este control existe precisamente para no reventar ese límite del lado del cliente.

Ambos perfiles preservan el conjunto completo de herramientas y la validación canónica del lado del servidor — solo cambian cuánta de esa información se *anuncia* por adelantado. En la sección 3.3 verás por qué esto importa especialmente al combinar REA con OpenCode.

### 1.4 Anatomía de la integración headless con los motores de backend

REA no reimplementa un desensamblador ni un descompilador: actúa como **orquestador** de motores existentes, cada uno con su propio modelo de proceso:

- **Ghidra**: REA abre el binario en una base de datos (DB) **efímera** dentro de una instancia Ghidra headless, pilotada por un bridge propio. Esta DB vive mientras dura la sesión; puede persistirse explícitamente con `snapshot_path` para reabrir el mismo estado de análisis más tarde sin reimportar el binario. Cada apertura verifica el **hash SHA-256** del artefacto contra una copia privada importada: si el archivo fuente cambia entre la apertura y una consulta posterior, la operación falla explícitamente con `artifact_changed` en lugar de devolver resultados sobre bytes distintos a los que crees estar analizando.
- **Hopper**: en macOS, REA puede incluso instalar Hopper por ti (con aprobación explícita) durante el setup. Aquí el modelo es "documento" en lugar de "base de datos efímera": Hopper puede pedir, en su primer arranque, elegir modo demo o activar la licencia — ese diálogo debe resolverse en la misma sesión de usuario antes de la primera operación CLI/MCP, algo a tener muy en cuenta si vas a automatizar jobs desatendidos (CI, cron).
- **IDA**: REA usa tu instalación existente de IDA (no instala ni actualiza IDA ni Hex-Rays) y ofrece opcionalmente un **puente MCP nativo** para IDA — un bridge más directo que una invocación batch por línea de comandos. Aquí entra el conocimiento general de la industria: el equivalente "headless" clásico de IDA es `idalib`/`idapython` en modo batch, el mecanismo que un bridge de este tipo normalmente envuelve para extraer pseudocódigo de Hex-Rays, xrefs y metadatos de tipos sin abrir la GUI.
- **Kuna**: un descompilador adicional soportado como proveedor nativo; REA documenta explícitamente qué capacidades le faltan frente a Ghidra (por ejemplo, no expone observaciones nativas de *def-use* para `trace_native_values`) — cada motor expone un subconjunto distinto de hechos, y REA declara explícitamente cuándo una capacidad no está disponible para el proveedor activo en lugar de simularla.
- **JEB**: aquí la relación se invierte — es el usuario quien arranca un cliente JEB sirviendo su propio servidor MCP, indicado a REA vía `REA_JEB_MCP_URL`. REA no lanza ni gestiona el proceso JEB.
- **objdump (GNU binutils) y Rizin**: proveedores "caller-supplied" para inspección nativa offline, sin licencia comercial ni GUI.
- **pwntools**: layout ELF offline (secciones, segmentos, símbolos y reubicaciones originales) y volcados de crashes Linux grabados (registros y señales por hilo), en Linux x64.
- **LLDB** (macOS): para observación dinámica acotada (`observe_native_calls`): REA lanza el Mach-O como proceso **nuevo y propio** bajo LLDB, coloca breakpoints en símbolos o selectores Objective-C exactos, registra argumentos de registro ABI y clase del receptor (vía el runtime Objective-C, sin evaluar expresiones). REA nunca se adjunta a un proceso que no lanzó él mismo.

### 1.5 Gestión de sesiones y estado del espacio de direcciones virtual

El ciclo típico es `open_binary` → una o varias herramientas de inspección sobre esa sesión → cierre o snapshot. Puntos clave:

- **Identidad por hash, no por ruta**: la sesión recuerda el SHA-256 del artefacto al abrirlo. Reabrir el mismo target y perfil reutiliza la base de datos viva, anotaciones incluidas — pero eso no hace esas ediciones elegibles automáticamente para un snapshot inmutable. El cierre con snapshot drena peticiones pendientes del proveedor antes de guardar; una edición concurrente exitosa durante ese drenaje rechaza el guardado y deja la sesión editada abierta (usa `export_evidence_bundle` para no perder esas observaciones antes de reabrir).
- **Direcciones como texto canónico**: Ghidra acepta hex con o sin `0x`, en cualquier capitalización, incluidos espacios de direcciones explícitos (`EXTERNAL:0x1`); los resultados normalizan a hex canónico en minúsculas. Un prefijo `0x` explícito selecciona dirección; si no, un nombre exacto de símbolo tiene prioridad sobre una dirección hex "desnuda" — una función renombrada a `dead` sigue siendo seleccionable por nombre sin ambigüedad con `0xdead`.
- **Regex y presupuestos de cómputo**: las búsquedas regex sobre Ghidra usan semántica `java.util.regex`; si compilar o emparejar agota la pila, REA devuelve una restricción de recurso y preserva la base de datos activa. Hopper e IDA comparten controles de *deadline* (`REA_REGEX_MATCHING_DEADLINE_MS`, 5000 ms por defecto) y de heap de worker (`REA_REGEX_WORKER_HEAP_REQUEST_MIB`, 128 MiB por defecto).

### 1.6 Binarios grandes sin colapsar la ventana de contexto

Este es el punto de diseño más relevante para quien construye flujos de agente sobre REA. El problema: el pseudocódigo de una función compleja o un grafo de xrefs grande pueden pesar varios megabytes — hay un ejemplo documentado de un grafo de interfaz de \~6.7 MB (\~2M tokens) para una sola app. Entregar eso inline reventaría cualquier ventana de contexto razonable.

La solución tiene tres capas:

1. **`detail: "summary"` como parámetro universal**: herramientas de volumen potencialmente grande (`procedure_pseudo_code`, `procedure_references`, `trace_feature`, `trace_native_values`, `batch_decompile`, `decode_interface_builder`…) aceptan este flag. La llamada retiene la observación **completa** en el servidor, pero solo devuelve conteos, identidades y un `parent_evidence_id` — nunca descarta trabajo.
2. **`inspect_analysis_view` para paginar**: con ese `parent_evidence_id`, pides vistas acotadas (p. ej. `{"kind": "native", "facet": "pseudocode", "offset": 0, "limit": 20000}`) y sigues `coverage.next_offset`. Los offsets cuentan **unidades de código UTF-16**, no líneas ni tokens, así que el paginado es determinista. Cada página reutiliza la observación retenida sin repetir la decompilación.
3. **Presupuestos duros con razones explícitas**: existe un límite de proyección de 1 MiB para muchas vistas acotadas, y para `trace_native_values` hay presupuestos independientes de profundidad (`max_depth`), funciones (`max_functions`), sitios de llamada (`max_call_sites`), nodos (`max_nodes`) y aristas (`max_edges`), más cotas fijas de payload por nodo (8 MiB) y resultado serializado (32 MiB). Cuando una traza se trunca, `traversal` siempre declara `truncated` con las razones exactas en vez de fallar silenciosamente.

Para exportar un binario entero sin pasar por la ventana de contexto, `decompile_all` (`rea decompile-all <target> --output <dir>`) escribe **un archivo de pseudocódigo por función en disco** y devuelve solo un manifiesto: conteos, directorio de salida, razones de fallo acotadas, identidad del proveedor y el digest del perfil de análisis. Soporta `--resume` (por SHA-256 + proveedor + perfil + layout) y mantiene un `decompile-journal.jsonl` append-only con cada intento, incluso fallidos. Esta es exactamente la estrategia correcta cuando OpenCode necesita razonar sobre miles de funciones: el agente nunca carga el binario completo en su contexto, sino que recorre el índice en disco bajo demanda.
